# Raymobtime Dataset Structure

## Overview

This document describes the structure of the datasets generated by Raymobtime. The output directory combines mobility information, wireless ray-tracing results, RGB images, LiDAR point clouds, channel representations, beamforming results, and post-processed data.

The exact set of generated directories depends on the features enabled in `config.yaml`. A dataset generated only with mobility and ray tracing will not contain the same files as a multimodal dataset that also enables RGB images, LiDAR, channel generation, and beam processing.

# 1. Database Output — `db/`

The `db/` directory contains structured simulation information used to organize the relationship between episodes, scenes, dynamic objects, transmitters, receivers, and generated outputs. Depending on the active Raymobtime version, the directory may contain a database file, SQL-related resources, serialized tables, or intermediate records created during the orchestration process.

Typical information stored in this stage includes:

* episode identifiers;
* scene identifiers;
* simulation timestamps;
* object identifiers;
* SUMO vehicle or pedestrian names;
* transmitter and receiver assignments;
* object positions;
* object dimensions;
* object orientations;
* validity information;
* line-of-sight information;
* references to generated files.

The database is primarily an internal organization resource. It should not be interpreted independently without considering the configuration and the coordinate files generated for the same simulation.

> **Note:** The exact database schema may change between Raymobtime versions. Any code that reads the database should refer to column or field names instead of depending exclusively on their positional order.

# 2. Coordinate Data — `coord/`

The `coord/` directory contains the position and association information generated during the mobility and placement stages. These files are used to relate each communication channel, image, or LiDAR scan to its corresponding transmitter, receiver, episode, and scene.

A coordinate file may contain fields such as:

| Field         | Description                                                    |
| ------------- | -------------------------------------------------------------- |
| `valid`       | Indicates whether the corresponding channel or sample is valid |
| `episode_id`  | Identifier of the episode                                      |
| `scene_id`    | Identifier of the scene                                        |
| `receiver_id` | Receiver index within the scene or episode                     |
| `object_name` | SUMO identifier of the associated object                       |
| `x`           | Horizontal X coordinate                                        |
| `y`           | Horizontal Y coordinate                                        |
| `z`           | Vertical coordinate                                            |
| `los`         | Line-of-sight indicator                                        |
| `orientation` | Object orientation, when available                             |
| `object_type` | Car, bus, truck, pedestrian, drone, or another type            |
| `timestamp`   | Simulation time associated with the scene                      |

The coordinate system must be consistent with the transformations used among SUMO, Blender, Blensor, and Wireless InSite.


> **Important:** Coordinate files should be preserved even when only the final beam or channel output is required. They provide the spatial reference needed to interpret and reproduce the dataset.

# 3. Ray-Tracing Data — `hdf5/`

The HDF5 format is used to store a large number of propagation paths efficiently while preserving the relationship between scenes and transmitter–receiver pairs.

A conventional ray-tracing tensor can be represented as:

```text
[
    number_of_scenes,
    number_of_tx_rx_pairs,
    maximum_number_of_paths,
    number_of_path_parameters
]
```

Each entry along the path dimension represents one propagation ray between a transmitter and a receiver.

The stored path parameters may include:

| Index | Parameter                    | Typical unit       |
| ----: | ---------------------------- | ------------------ |
|     0 | Received power               | dBm                |
|     1 | Time of arrival              | seconds            |
|     2 | Elevation angle of departure | degrees            |
|     3 | Azimuth angle of departure   | degrees            |
|     4 | Elevation angle of arrival   | degrees            |
|     5 | Azimuth angle of arrival     | degrees            |
|     6 | Line-of-sight flag           | Boolean or integer |
|     7 | Ray phase                    | degrees            |

The line-of-sight field is typically represented as:

```text
1 = line-of-sight path
0 = non-line-of-sight path
```

Depending on the Wireless InSite version and parser configuration, additional information may be stored, such as:

* vehicle orientation;
* path identifiers;
* propagation interactions;
* transmitter and receiver indices;
* carrier frequency;
* total path loss;
* complex electric-field components.

Because different transmitter–receiver pairs may contain different numbers of paths, the tensor normally uses a configured maximum number of rays. Missing paths may be padded with zeros or another predefined invalid value.

> **Important:** Consumers of the HDF5 file must distinguish between valid propagation paths and padded entries. The selected padding convention should be documented with the dataset.

## 3.1 Relationship with Coordinates

The HDF5 channel index must be associated with the corresponding coordinate entry.

The relationship is generally determined using some combination of:

```text
episode_id
scene_id
transmitter_id
receiver_id
channel_index
```

Filtering or reordering the coordinate file without applying the same operation to the HDF5 data may break the spatial correspondence between samples.

## 3.2 Inspecting the HDF5 File

A simple inspection can be performed with Python:

```python
import h5py

with h5py.File("ray_tracing_data.h5", "r") as hdf5_file:
    print(list(hdf5_file.keys()))

    for key in hdf5_file.keys():
        dataset = hdf5_file[key]
        print(key, dataset.shape, dataset.dtype)
```

The actual dataset keys depend on the version of the HDF5 generation module.

# 4. Raw RGB Images — `blensor/image/`

The `blensor/image/` directory stores RGB images rendered from the Blender scenario.

Depending on the selected configuration, images may be generated from:

* base-station cameras;
* user-equipment cameras;
* both base-station and user-equipment viewpoints.

Example:

```text
outputs/
└── blensor/
    └── image/
        ├── BS/
        │   ├── Camera0/
        │   ├── Camera1/
        │   └── Camera2/
        └── UE/
            ├── episode_000/
            └── episode_001/
```

## 4.1 Base-Station Images

For base-station image generation, the cameras are manually created and positioned in the Blender base scenario.

Typical camera names are:

```text
Camera0
Camera1
Camera2
```

Each camera captures the scenario from a fixed base-station viewpoint.

The number of base-station cameras must match the value configured in Raymobtime.

## 4.2 User-Equipment Images

For user-equipment image generation, Raymobtime automatically creates or positions the cameras according to the receiver coordinates generated during the mobility stage.

Therefore, the base `.blend` file does not need to contain one manually configured camera for every UE position.

# 5. Raw LiDAR Data — `blensor/lidar/`

The `blensor/lidar/` directory contains the raw point clouds generated by the Blensor sensor simulation. The raw output may use formats such as:

```text
.pcd
.txt
.npy
.npz
```

A point cloud normally contains Cartesian coordinates:

```text
x, y, z
```

Depending on the selected sensor and export settings, it may also contain:

* distance;
* intensity;
* object identifier;
* timestamp;
* scan angle;
* noise information;
* return index.

## 5.1 Sensor Reference Frame

Raw LiDAR points may initially be expressed in:

* the LiDAR sensor frame;
* the Blender world frame;
* another intermediate coordinate system.

The reference frame must be documented because it determines how the point cloud is aligned with receiver coordinates, images, and wireless channels.

## 5.2 Variable Number of Points

The number of returns may vary between scans because of:

* sensor position;
* occlusion;
* maximum scanning distance;
* scene geometry;
* dynamic-object placement;
* angular resolution;
* sensor noise.

For this reason, raw scans may not have a fixed tensor shape until post-processing is applied.

## 6.1 Processed Images — `post_processing/refined_images/`

The image post-processing stage refines the RGB images generated from the Base Station cameras. Its main purpose is to identify the receivers in each camera view and generate visual annotations that associate the rendered images with the corresponding mobility and coordinate data.

The current implementation processes only Base Station images. For each valid receiver, Raymobtime projects its three-dimensional position from the global scenario coordinate system into the image plane of every configured Base Station camera.

The refinement process uses:

* the receiver coordinates stored in `CoordVehicleTxRx.csv`;
* the Base Station camera parameters stored in `cam_info.json`;
* the detailed object geometry stored in the Raymobtime database;
* the raw RGB images generated for each simulation run.

### Receiver Markers

The `marker/` directory contains copies of the original Base Station images with a marker placed at the projected position of the corresponding receiver.

For each receiver, Raymobtime:

1. reads its global position from the coordinate file;
2. transforms the position into the camera reference frame;
3. projects the three-dimensional point into pixel coordinates;
4. verifies whether the projected point is inside the image;
5. draws a marker when the receiver is visible.

If the receiver is outside the camera field of view or behind the camera, the original image is saved without a marker.

### Receiver Bounding Boxes

The `bb/` directory contains images with a bounding box around the detailed object associated with the receiver.

The bounding box is generated using the vertices of the corresponding Wireless InSite object stored in the Raymobtime database. Each vertex is projected into the camera image, and the minimum and maximum visible pixel coordinates are used to define the rectangular region around the object.

This process produces annotations for objects such as vehicles represented by the selected receiver.

If the object is not visible in the selected camera, the original image is saved without a bounding box.

### Camera Projection

The projection process uses the camera position, orientation, focal length, sensor dimensions, and image resolution.

For each camera, Raymobtime generates an intrinsic matrix of the form:

```text
K =
[
    fx  0  cx
    0  fy  cy
    0   0   1
]
```

where:

* `fx` and `fy` are the focal lengths expressed in pixels;
* `cx` and `cy` are the coordinates of the image center.

The receiver position is first transformed from the global scenario coordinate system into the camera reference frame and then projected into the image plane.

### Receiver Positions in the Camera Frame

In addition to the annotated images, Raymobtime stores the receiver positions expressed in the coordinate system of each Base Station camera.

The resulting file is:

```text
RxPosCamraPOV.npz
```

The stored array follows the organization:

```text
[
    number_of_episodes,
    number_of_scenes,
    number_of_receivers,
    number_of_cameras,
    3
]
```

The final dimension contains the receiver coordinates in the camera frame:

```text
x_camera
y_camera
z_camera
```

Positions that are not available remain represented by `NaN`.

> **Note:** This post-processing stage currently applies only to Base Station images. User Equipment images are generated using cameras positioned automatically from the receiver coordinates, but they are not processed by the current marker and bounding-box refinement function.

> **Important:** The image annotations depend on the spatial alignment among the coordinate data, Blender cameras, detailed object geometry, and raw images. Incorrect camera parameters, object positions, or coordinate-system transformations may produce displaced markers or bounding boxes.

# 7. Processed LiDAR Data — `post_processing/lidar/`

The `post_processing/lidar/` directory contains point clouds converted into the representation selected for the final dataset.

Possible operations include:

* coordinate-frame conversion;
* translation relative to the receiver or base station;
* removal of invalid points;
* point-cloud cropping;
* distance filtering;
* quantization;
* voxelization;
* normalization;
* compression;
* conversion from PCD to NumPy;
* synchronization with the communication channels;
* grouping by episode and scene.

Example:

```text
post_processing/
└── lidar/
    ├── point_clouds/
    ├── quantized/
    ├── metadata/
    └── lidar_data_<scenario_id>.npz
```

A processed LiDAR dataset may use a structure such as:

```text
[
    number_of_samples,
    maximum_number_of_points,
    3
]
```

or a quantized representation such as:

```text
[
    number_of_samples,
    x_bins,
    y_bins,
    z_bins
]
```

The selected format depends on the post-processing method.

## 7.1 Point-Cloud Association

Each processed point cloud should be associated with:

```text
episode_id
scene_id
receiver_id
sensor_id
```

Example metadata:

```csv
sample_id,episode_id,scene_id,receiver_id,lidar_file
0,0,12,3,point_cloud_000000.npy
```

## 7.2 Coordinate Transformation

When point clouds are translated to a local coordinate system, the transformation should be recorded.

For example:

```text
p_local = p_world - p_receiver
```

The dataset documentation should state whether the processed points are represented relative to:

* the global scenario origin;
* the transmitter;
* the receiver;
* the LiDAR sensor.

# 8. Beam and Channel Post-Processing — `post_processing/beams/`

The `post_processing/beams/` directory contains the channel matrices and beamforming results derived from the Wireless InSite propagation paths.


The three stages represent:

```text
Ray-tracing paths
        ↓
H-matrix generation
        ↓
Codebook application
        ↓
Beam scores and selected beams
```

## 8.1 MIMO Channel Matrices — `beams/h_matrix/`

The `h_matrix/` directory contains the narrowband MIMO channel matrices generated from the propagation paths produced by Wireless InSite.

For each valid scene and transmitter–receiver pair, Raymobtime constructs one channel matrix before applying the transmitter and receiver codebooks. 

### 8.1.1 Stored Data

For each scene index `s` and receiver index `r`, Raymobtime stores the raw MIMO channel as:

```python
hmatrix[s, r] = mimoChannel
```

Therefore, the complete H-matrix dataset can be interpreted conceptually as:

```text
[
    number_of_scenes,
    number_of_receivers,
    number_of_rx_antennas,
    number_of_tx_antennas
]
```

or, when episodes are represented explicitly:

```text
[
    number_of_episodes,
    number_of_scenes,
    number_of_receivers,
    number_of_rx_antennas,
    number_of_tx_antennas
]
```

The exact outer dimensions depend on how scenes and episodes are organized by the calling module. However, the final two dimensions always represent:

```text
[N_rx, N_tx]
```

### 8.1.2 Complex Representation

The H-matrix contains complex-valued coefficients.

Depending on the output serialization, the data may be stored using:

```text
complex64
complex128
```

or separated into real and imaginary components:

```text
H_real
H_imag
```

The complex matrix preserves both amplitude and phase information and should not be replaced by its magnitude before codebook processing.

# 9. Beamformed Channel Output — `beams/channel_output/`

The `channel_output/` directory contains the magnitude of the equivalent channel obtained after applying the transmitter precoding codebook and the receiver combining codebook to the MIMO channel matrix. The output contains one channel response for each combination of transmitter and receiver codewords.

The internal matrix dimensions are:

```text
[
    number_of_rx_codewords,
    number_of_tx_codewords
]
```

Therefore:

* each row corresponds to one receiver combining codeword;
* each column corresponds to one transmitter precoding codeword;
* each matrix element contains the magnitude of the equivalent channel for that beam pair.

For example, with 64 transmitter codewords and 16 receiver codewords:

```text
channel output shape: [16, 64]
```

For the complete dataset, the conceptual structure is:

```text
[
    number_of_scenes,
    number_of_receivers,
    number_of_rx_codewords,
    number_of_tx_codewords
]
```

When episodes are represented explicitly, the structure may be:

```text
[
    number_of_episodes,
    number_of_scenes,
    number_of_receivers,
    number_of_rx_codewords,
    number_of_tx_codewords
]
```

> **Important:** The number of rows in each codebook must match the number of antenna elements of the corresponding side of the H-matrix. The number of columns defines the number of available codewords and, consequently, the dimensions of the channel-output matrix.

# 10. Best-Beam Output — `beams/beams/`

The `beams/` directory contains the index of the best beam pair selected from the beamformed channel output.

For each scene and receiver, Raymobtime computes the magnitude of the equivalent channel and selects the position with the highest value:

```python
beam_index = np.argmax(equivalent_channel_magnitude, axis=None)
```

The resulting value is stored as an integer:

```python
beamIndexOutputs[s, r] = int(beam_index)
```

Therefore, each stored beam value represents the linear index of the strongest transmitter–receiver codeword combination.

The conceptual dataset structure is:

```text
[
    number_of_scenes,
    number_of_receivers
]
```

When episodes are represented explicitly, the structure may be:

```text
[
    number_of_episodes,
    number_of_scenes,
    number_of_receivers
]
```

Each element contains one integer identifying the best beam pair for the corresponding communication channel.

Example:

```text
beamIndexOutputs[scene, receiver] = 75
```

The stored value does not directly contain separate transmitter and receiver beam identifiers. Instead, it corresponds to the flattened position of the maximum value in the channel-output matrix.

Since the channel-output matrix has the shape:

```text
[
    number_of_rx_codewords,
    number_of_tx_codewords
]
```

the receiver and transmitter codeword indices can be recovered using:

```python
rx_beam_index, tx_beam_index = np.unravel_index(
    beam_index,
    (
        number_of_rx_codewords,
        number_of_tx_codewords,
    ),
)
```

For example, for a channel-output matrix with:

```text
16 receiver codewords
64 transmitter codewords
```

and a stored beam index equal to:

```text
75
```

the corresponding beam pair is:

```text
receiver codeword index: 1
transmitter codeword index: 11
```

because the matrix is flattened row by row using NumPy's default C-order convention.

The beam index follows Python zero-based indexing:

```text
0, 1, 2, ..., N - 1
```

where:

```text
N = number_of_rx_codewords × number_of_tx_codewords
```  

> **Important:** The stored value is a flattened beam-pair index, not only a transmitter beam index. To recover the transmitter and receiver codewords separately, the dimensions and axis order of the corresponding `channel_output` matrix must be known.

> **Note:** When one side uses only a single antenna or does not apply a codebook, the beam index may effectively represent only the codewords of the other side.
